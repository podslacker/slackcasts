1️⃣ Overview

The session walks through how to take AI agents from prototype to production.
It is organized around four lifecycle buckets (Build, Scale, Govern, Optimize) and distilled into five practical principles that Google Cloud uses when deploying agents at scale. Real‑world examples from Ford Credit illustrate the end‑to‑end flow.

2️⃣ Major Sections & Core Topics

Section Key Points
⚡ Intro – The “gravity” of today’s AI software • Software development has accelerated dramatically in the last year.
• Moving from “building agents” (2023) to building systems around agents (2024) – resilient, secure, production‑ready.
🔧 Principle 1 – Jump‑start agent building • Persona‑centric tooling – match the creator’s skill level:
- Subject‑matter experts: Agent Studio (visual drag‑and‑drop).
- Low‑code developers: Agent Garden (pre‑built samples).
- Hardcore engineers: Agent Development Kit (ADK) + Agent CLI for code‑first work.
• Goal: give the right tool to the right person to lower adoption friction.
🧩 Principle 2 – Separate concerns (MCP, A2A, Skills) • MCP (Model‑Control‑Protocol) – abstraction layer between an agent and external APIs/tools. Prevents tight coupling; changes in APIs don’t force agent rewrites.
• A2A (Agent‑to‑Agent) – a protocol for delegating tasks between agents without custom glue code.
• Skills – a markdown‑based bundle of business rules, data, and resources that agents can load on‑demand, keeping context windows small and latency low.
🚀 Principle 3 – Scale the agent • Decide memory strategy:
- Stateless (no short‑/long‑term memory) for simple lookup agents.
- RAG pipelines for custom long‑term memory (compliance‑heavy use cases).
- Platform‑provided: Agent Platform Sessions (short‑term, 365‑day TTL) + Memory Bank (vector DB, async, configurable TTL).
• Choose runtime wisely:
- Agent Platform Runtime (full feature set, built‑in security, memory).
- Bring‑Your‑Own‑Container (7‑day TTL).
- Cloud Run for Docker portability.
- GKE only for massive fleets.
🔐 Principle 4 – Govern through infrastructure, not prompts • Prompt‑based guardrails are brittle.
• Four governance layers:
1. Agent Identity – SPIFFE‑backed IDs, automatic OAuth2/API‑key handling.
2. Agent Registry – single pane of glass for all agents & tools.
3. Agent Policies – IAM‑style permissions + natural‑language policies.
4. Agent Gateway – central traffic‑monitoring gate that enforces policies.
📈 Principle 5 – Observability & Evaluation • Production agents need logs, traces, metrics (Google Cloud Operations suite).
• Evaluation goes beyond output correctness: track trajectory (right steps, time, cost, compliance). Can be human‑defined or LLM‑based.
🚗 Ford Credit case study (Siddharth Jain) • How Ford Credit integrated the above principles to ship a credit‑risk assistant at scale. (Details omitted in transcript excerpt.)

3️⃣ Key Takeaways

# Takeaway
1️⃣ Tool‑persona alignment accelerates adoption – give non‑coders visual tools, give engineers a full SDK.
2️⃣ MCP, A2A, and Skills act as “thin‑waist” abstractions that decouple agents from volatile downstream services.
3️⃣ Memory is optional; choose the simplest approach that satisfies the use case (stateless → RAG → Platform memory).
4️⃣ Runtime selection should be driven by feature needs (memory, human‑in‑the‑loop, long‑running ops) and cost, not by hype.
5️⃣ Governance is infrastructure‑first – use identities, registries, policies, and a gateway instead of relying on prompt tricks.
6️⃣ Observability is mandatory – capture end‑to‑end telemetry and evaluate both what the agent says and how it got there.
7️⃣ Buy vs. build decisions should be revisited at each bucket (build, scale, govern, optimize) to avoid over‑engineering.

JORDAN: By reducing friction. If a business analyst can drag‑and‑drop a workflow, they can prototype faster, then hand off the exported definition to engineers for polishing and deployment. No one bottlenecks the pipeline.

MIKE: Moving on to scaling, the talk emphasized “separating concerns”—MCP, A2A, and skills. I liked the analogy of an abstraction layer between the agent and external APIs.

MIKE: And “skills” are essentially markdown files that bundle business rules and resources, loading them on demand to keep the LLM’s context window lean. That sounded like a neat hack to cut latency and cost.

JORDAN: The managed Memory Bank is a vector DB with asynchronous indexing, so you get semantic search without adding latency to the user request. Plus, you can set TTLs to control how long data lives.

MIKE: Runtime choices were the next big decision—local, Cloud Run, GKE, or the Agent Platform Runtime. The guiding principle was “don’t over‑engineer before you need to.”

JORDAN: And the platform runtime even lets you bring your own containers, giving a 7‑day TTL for long‑running tasks. It’s a nice middle ground between fully managed and fully custom.

MIKE: Governance came across as the most critical—no more “just add a prompt to prevent bad behavior.” They’re using infrastructure: SPIFFE‑backed agent identity, a central registry, IAM‑style policies, and an Agent Gateway that enforces everything.

JORDAN: That separation of visibility, control, and security through actual services rather than prompt engineering is a game changer for compliance‑heavy industries.

MIKE: Finally, observability and evaluation—logs, traces, metrics, plus testing the agent’s trajectory, not just its output. It’s like moving from unit tests to integration tests for AI.

JORDAN: Summing up, the path to production involves the right tooling for creators, clean abstraction layers for reliability, managed memory and runtimes for scalability, strict infrastructure‑based governance, and thorough observability.

MIKE: If you’re thinking about deploying an AI agent in your own organization, start by matching the tool to the user, then build the glue‑less architecture they described, and let the platform handle the heavy lifting.

JORDAN: That’s the takeaway: make agents modular, secure, and observable from day one, so you can iterate fast without drowning in technical debt.
